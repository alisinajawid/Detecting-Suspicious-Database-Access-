# Database Access Anomaly Literature

This focused review of **14 primary studies from 2017–2026** shows that database-access anomaly detection has already been studied, so the project should not claim to be the first to apply machine learning to database logs. The closest work uses real database traces for normal behavior but injects or generates anomalies because labeled operational attacks are scarce; other studies use SQL intent or application-specific profiles. Evidence supports a reproducible comparison of Isolation Forest, Local Outlier Factor, and One-Class SVM on session-level PostgreSQL audit features, but published metrics cannot predict this prototype’s performance. The most urgent design issue is that the Phase 1.3 scenario labels use the same measurements currently planned as model inputs. Addressing that circularity before data generation will make the results more credible than adding model complexity.

## Database studies use real behavior and constructed anomalies

Direct database research confirms that session and query activity can support anomaly detection, while exposing the limits of available labels. Gutflaish and colleagues’ temporal database anomaly work used two months of live user-table access records, but the records contained no known anomalies; the researchers inserted synthetic access-time changes to test temporal detection. Their Temporal Likelihood Regression method did best on the unusual-time experiment, while most tested baselines performed close to random when they lacked a temporal model. This is relevant to the project’s time scenario, though the data were hourly user-table matrices rather than query-by-query PostgreSQL audit events. ([Gutflaish et al., 2019](https://doi.org/10.1609/aaai.v33i01.33013755))

The closest operational study is UCAD, which learned contextual behavior from real session traces in two Internet-company database applications and generated anomalous sessions because the authors found no public database-operation anomaly dataset and collected few real anomalies. It reports F1 scores of **0.89693 and 0.98168** in its two scenarios, outperforming its tested baselines, including Isolation Forest and One-Class SVM. The authors also report false positives for rare normal patterns in some production settings and assume that operation logs remain reliable and intact. Its traces are not public, and its stronger contextual sequence model is not a direct result for the simpler features proposed here. ([Li et al., 2022](https://doi.org/10.1145/3514221.3517861))

Two more recent database studies reinforce the need for caution when interpreting benchmark numbers. Abed compares LOF, One-Class SVM, and Isolation Forest using PostgreSQL-derived data from one university, but each constructed dataset contains only **20 anomaly rows**; the reported anomaly-class accuracy varies sharply across models and is near zero for Isolation Forest and One-Class SVM. **Review interpretation:** the small positive class makes those estimates unstable. ([Abed, 2024](https://doi.org/10.37899/journallamultiapp.v5i6.1538)) Wang and colleagues compare TF-IDF plus the same three classical detectors with a more elaborate SQL-intent model on synthetic and semi-real power-grid SQL logs. On their semi-real set, the full method reports **0.56 AUPRC and 0.69 recall at 1% false-positive rate**, while TF-IDF plus Isolation Forest reports 0.19 AUPRC and 0.34 recall at that false-positive rate. These are query-level SQL-intent results from one specialized environment, not session-level behavioral results; the authors identify offline batch evaluation and temporal modeling as future work. ([Wang et al., 2026](https://doi.org/10.1049/cmu2.70172))

Bossi and colleagues provide earlier, useful context through DetAnom, which profiles database access patterns of application programs rather than comparing machine-learning detectors on user sessions. Its PostgreSQL experiments use generated Java applications. The paper reports near-accurate profiling and low runtime overhead, while noting that incomplete profiles can miss anomalies and concolic profile generation can become slow or grow exponentially. It is relevant to database-specific detection, but its threat model and evaluation are different from this project’s. ([Bossi et al., 2017](https://doi.org/10.1109/TSE.2016.2598336))

## Insider-threat results depend on synthetic data and evaluation choices

CERT insider-threat studies offer useful design lessons because they aggregate user activity into daily, weekly, or session-level behavior, but CERT simulates organizational logs such as logons, email, web, files, and removable devices. It is not a database-query benchmark. Li and colleagues’ image-based method improves AUROC by a reported **4% at instance level and 2% at user level** over its autoencoder comparator on CERT r4.2, but the authors note that scenario-specific feature selection can miss a threat when relevant behavior is absent from the feature vector. ([Li et al., 2021](https://doi.org/10.1155/2021/1777536)) ACOBE combines per-user and group behavior over multiple days and reports **99.99% ROC-AUC** on a synthesized CERT evaluation with four abnormal users among 929. Its enterprise case study inserts controlled malware traces into otherwise attack-free logs; the authors describe it as demonstrating applicability to logs, not validating insider detection with naturally occurring attack labels. ([Yuan et al., 2021](https://doi.org/10.1109/DSN48987.2021.00038))

Other CERT studies show why the project should report minority-class and false-alarm performance rather than accuracy alone. Bertrand and colleagues report **88.38% recall, 93.08% accuracy, 6.9% false-positive rate, and 0.958 AUC** for a per-user Bayesian Gaussian mixture approach, but describe using the full dataset for unsupervised training and detection. ([Bertrand et al., 2023](https://doi.org/10.1109/PST58708.2023.10320169)) Al-Shehari and colleagues report 98% accuracy, 98% detection, and 99% F-score for an Isolation Forest setting; their decision-tree baseline has higher accuracy (99%) but only 64% detection and 66% F-score. Their paper also contains a stated contamination ratio that conflicts with its reported sample counts, so the high scores should not be treated as a reproducible target without checking the split and data preparation. ([Al-Shehari et al., 2023](https://doi.org/10.1109/ACCESS.2023.3326750)) A 2025 arXiv preprint combines a Transformer representation with LOF, One-Class SVM, and Isolation Forest and reports 96.38% F1 and 5.71% false-positive rate for its Isolation Forest configuration; its authors identify synthetic data, imbalance, and missing real-world validation as limitations. ([Elbasheer & Akinfaderin, 2025](https://arxiv.org/abs/2506.23446))

Synthetic scenario design also appears in supervised work. Gayathri and colleagues use conditional-GAN augmentation on CERT and report F-scores of 0.759 and 0.763 for two augmented multi-class models. They explicitly state that their simple feature set does not capture complete behavior and that one dataset is insufficient to prove general conclusions. ([Gayathri et al., 2021](https://doi.org/10.1109/TrustCom53373.2021.00105)) These studies support controlled experiments as a practical way to evaluate rare events, but their scores are not directly comparable: they differ in labels, aggregation units, class balance, feature sets, data splits, and metrics.

## Cross-domain comparisons show no universal model winner

Studies outside database access are useful for understanding the three selected algorithms, but they do not establish expected performance on PostgreSQL logs. McGuan and colleagues compare One-Class SVM, Isolation Forest, and LOF across two simulated industrial-control platforms. Results change substantially between platforms: on GRFICSv2, One-Class SVM reaches 88.9% true-positive rate at 0% false-positive rate, Isolation Forest reaches 18.4% at 0%, and LOF reaches 100% true-positive rate with a 100% false-positive rate. ([McGuan et al., 2023](https://doi.org/10.1109/ISI58743.2023.10297207)) The Automotive Ethernet study finds that all three classical methods perform poorly on its packet-sequence datasets, which the authors attribute to high-dimensional and irrelevant features; it uses replay attacks from one physical testbed, limiting generalization. ([Alkhatib et al., 2022](https://doi.org/10.1109/IV51971.2022.9827285))

A 2024 unknown-attack detection study evaluates one-class methods across ten public network-intrusion datasets and reports macro-F1 scores of 99.37% and 97.65% for its own method on two ToN-IoT datasets, with results varying by dataset. Its future work includes hierarchical multi-class identification and better synthetic attack-noise generation. ([Uddin et al., 2024](https://doi.org/10.1038/s41598-024-80021-0)) Together, these studies show that model ranking depends on the data representation, scenario, threshold, and acceptable false-positive rate. They support comparing the same models on one common feature set and reporting precision, recall, F1, false-positive rate, and scenario-level outcomes. They do not justify importing their scores or claiming that one detector should win in the database project.

## The defensible gap is a transparent database-specific baseline

Across this focused set of 14 papers, I did not find a study that provides a reproducible head-to-head comparison of Isolation Forest, LOF, and One-Class SVM on session-level PostgreSQL audit features for all five scenarios in the project plan. This is a bounded literature review, not proof that no such study exists. The contribution should therefore be stated narrowly: **a reproducible controlled comparison on a documented PostgreSQL/FastAPI audit-log dataset, with held-out normal and suspicious sessions, per-scenario metrics, and explicit false-positive reporting**. It is an applied dataset-and-evaluation contribution, not a new anomaly-detection algorithm.

Before generating data, revise the Phase 1.3 label design. At present, the high-query label is defined by `queries_per_hour`, large extraction by row/byte totals, unusual time by `after_hours_event_count`, repeated failures by failed-event counts, and unusual-table access by the corresponding table-access features. Because those same features are model inputs, the evaluation can become circular: the model is tested on whether it recovers the rule used to create the label. Keep scenario identity as evaluation-only metadata, define anomalies through controlled injection and user-profile context, and preplan an ablation that removes each scenario’s direct proxy feature. Include a simple threshold-rule baseline beside the three ML models. Train or calibrate using normal sessions only, hold out separate generated sessions, and report both full-feature and ablated results. These steps will show whether the models detect broader patterns beyond reproducing the generator’s thresholds.

## Conclusion

The literature makes the project’s strongest contribution its **transparent dataset and evaluation design**, not algorithm novelty. Before implementation, fix the scenario-to-feature circularity and predefine a normal-only training split, a threshold-rule baseline, and feature ablations. Then the model comparison can answer a useful applied question: which database-access behaviors these detectors identify on this controlled prototype, and at what false-positive cost.
